# Decisions for the web version (2026-09-12)

Recorded so they can be revisited. Numbered for reference.

1. **Original files untouched.** The web build lives in `webapp/`; the engine
   modules were *copied* into `webapp/engine/` and the desktop app in the
   repo root still works as before (on Python 2).
2. **Python 3 port by shims, not rewrite.** The core modules (Play, GameManager,
   ResultofthePlay, YardageTable, Die, Penalty, PickAPlayer, LogPlays, ...)
   compiled under Python 3 unchanged. Only two edits: numpy's
   `random.normal` replaced with `random.gauss` (drops the numpy dependency)
   and one integer-division fix in `TimeOutProcessing`. Tkinter, tkMessageBox,
   the turtle field and the Scoreboard class are replaced by headless stand-ins
   in `webapp/engine/` that write to `bus.py` instead of widgets. This keeps
   the simulation logic byte-for-byte the author's.
3. **ControlPanel.py re-implemented as `game.py`.** Every button handler is a
   method; module globals became attributes. The two questionable globals in the
   original (`TeamStats` being reset to a 2-key dict on kickoffs, `PlayerStats`
   being None for kicks) are replaced with the full dicts every time; a superset
   is harmless and avoids KeyErrors in end-of-game paths.
4. **Team selection by dropdown, not `Team Selection.xlsx`.** Any uploaded
   `<Team>.xlsx` that is not a simulator output is a selectable team.
5. **Data directory = working directory.** The engine uses relative paths for
   all workbooks, exactly like the desktop app, so the server chdir()s into
   the data dir once. Uploads, team files, `General Info.txt`, and the output
   files (`*Log.xlsx`, `*log.xlsx`, `*Stats.xlsx`, `*DStats.xlsx`) all live there
   and are all visible/downloadable/deletable on the Files page.
6. **One game at a time, in process memory.** Gunicorn runs a single worker.
   A restart of the service loses a game in progress (not the data files).
7. **Popup messages become inline notices.** Every `showinfo` the desktop app
   raised (button-press infractions, penalty notices, "Game Over") shows as a
   blue notice under the scoreboard for that turn. `askyesno` for the
   last-play extra point always proceeds, which is what the original code
   effectively did (it compared the result to the string "no").
8. **Engine exceptions don't kill the game.** A traceback is shown on the page
   and the game continues; state may be inconsistent after one.
9. **Sample teams shipped.** `sample_data/SampleHome.xlsx` and
   `SampleAway.xlsx` are synthetic workbooks generated by
   `make_sample_data.py` in the exact layout the engine reads. They are copied
   to the data dir on first deploy so the app works before real data is
   uploaded. 48 simulated full games ran with zero engine errors
   (`simulate.py`). Overtime was never reached in those runs, and the original
   author flagged OT as possibly broken, so treat OT as untested.
10. **Hosting: one EC2 t3.micro, Ubuntu 24.04, us-east-1, Elastic IP, port 80,
    no domain, no HTTPS.** Protected by HTTP Basic auth (user `rick`, random
    password written to `deploy/.env` at provision time). HTTPS needs a domain;
    add later with Caddy or nginx+certbot if wanted. SSH is opened only to the
    IP that ran `provision.sh`.
11. **Deployment = tar over scp + systemd.** No Docker, no git on the server.
    `deploy/provision.sh` creates everything once; `deploy/push.sh` redeploys
    code; `deploy/teardown.sh` destroys the instance and IP (data on it is lost).
12. **Not done / out of scope for now:** the stats-extractor app (Executive.py,
    ESPN scraping), multi-user games, HTTPS, backups of the data dir, and the
    field graphic is a simple bar rather than the turtle drawing.

## Improvements round 1 (2026-09-12, after first deploy)

13. **Game history in SQLite + one folder per game.** `history.py` keeps
    `history.sqlite` in the data dir and `games/<id>/` holds the six output
    workbooks of each finished game, so games between the same teams no longer
    overwrite each other. Game id = timestamp + team names. The History page
    lists games, standings (W/L/T, points for/against) and per-game play logs.
    Abandoned games are recorded too (status only). The engine's scratch
    `*Log.xlsx` files are deleted at quit; they are recreated on every start.
    SQLite chosen over JSON files for cheap standings queries; no ORM.
14. **Reproducible games via a seeded journal.** The engine draws every random
    number from Python's global `random`, so `Game` seeds it once and appends
    every button press (action + checked boxes) to `games/<id>/journal.json`.
    Replaying the journal rebuilds the identical game. This gives (a) resume
    of the in-progress game after a restart or redeploy and (b) an Undo button
    that replays all but the last action. Chosen over pickling the engine state
    because the state is spread across openpyxl worksheets and module globals.
    Cost: undo replays the whole game (well under a second for a full game).
    Any future change to the engine's random call sequence invalidates old
    journals, which only matters for games in progress at the time.
15. **Bulk data in and out.** The upload form accepts a .zip (unpacked and
    flattened server-side, same .xlsx/.txt filter, paths stripped) or a whole
    folder via the browser's folder picker. "Download everything" returns a
    zip of the data directory including games/ and the history database. No
    chunked/resumable upload; the request limit stays 50 MB.
16. **Auto-play button.** Runs the naive coach from the test harness (kick when
    required, punt/FG on 4th and long) until the engine reports Game Over.
    Every action goes through the journal, so Undo works afterwards. The
    coach is deliberately dumb; it is for getting a result, not for strategy.
